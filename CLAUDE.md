# Velocity

*Authored by Gareth Hall and Claude. (Formerly "Portfolio Command Centre" — renamed 2026-05-13. The repo path and localStorage keys are unchanged to preserve existing sessions.)*

## What This Is
A zero-infrastructure, single-file HTML+JS portfolio management app for managing projects across multiple customer accounts. Runs client-side in the browser. Reads/writes JSON data with localStorage auto-save. The app is **customer-scoped** — `App.activeCustomer` is always a real working customer (every authoring/creation flow depends on it). The global header selector also offers an **"All customers"** option (`App.allCustomers` flag) that aggregates the read/overview + planning-list views — see "Customer scoping & the All filter" below. Demo data ships with three fictional customers (Acme Industries, Globex, Initech); rename or replace them in Settings → Customers. An optional, provider-agnostic AI layer adds an Assistant and governed generation skills — the app stays fully functional with no model configured.

## Files
- `index.html` — The complete single-file app (~52,000 lines). All CSS, HTML, and JS in one file.
- `portfolio-data.json` — Sample (fictional) data shipped with the repo for first-time loaders. For private/local data, drop a file matching `*.local.json` (gitignored).
- `portfolio-data-demo.json` — Same sample data, also embedded inline for the **Load demo dataset** button (file:// safe).
- `definitions/` — Governed template/definition files for AI skills (SOW sections + style, Tableau wireframe vocabulary + design rules, manifest of template sets). Authored files are the source of truth; `scripts/embed-definitions.mjs` mirrors them into `index.html` as data islands and `tests/unit/skills.test.mjs` fails on drift. **Run the script after any edit under `definitions/`.**
- `SOLVER.md` — Technical reference for the auto-allocation solver: settings, rules R1–R12, algorithm passes, warnings, scoring, and known limitations. Read this before tweaking `Solver.solve` or `Sprint.allocSettings`.
- `SKILLS.md` — How to add a skill, a template/definition set, or an AI provider adapter. Read this before touching `AI`, `AgentTools`, `Skills`, `Sow`, or `Wireframe`.

## Architecture
- **Single HTML file** — no build step, no dependencies, no framework. Opens directly in any browser.
- **Views**: Dashboard/Projects (shared DOM container with a `view-mode-*` class toggling section visibility), Backlog, Sprint Planning, **Board (Kanban)**, Roadmap/Gantt, Capacity & Workload, **RAID** (tabs: Risks/Assumptions/Issues/Decisions/Actions — the former standalone Actions view is folded in as the Actions tab; `navigate('myactions')` aliases here), Documents, Strategy (Objectives/Personas/Metrics/Products), Activity, Configuration. The Governance view + `navigate('governance')` still exist (reached via RAID-decision deep-links and the palette) but are no longer a sidebar item. Plus the dockable **Assistant** panel (Ctrl/Cmd+J) available on every view.
- **Data model**: Projects → Delivery Config → Phases/Skills → Sprints. Team Members with flexible capacity. Governance Meetings with project mapping.
- **JS modules**: `App` (core), `Dashboard`, `DetailPanel`, `Gantt`, `Sprint`, `Capacity`, `Governance`, `Solver`, `AuditPanel`, `TrendsModal`, `ProjectWizard` (conversational new-project onboarding), plus the agentic layer: `AI` (provider adapters), `AgentTools` (tool registry), `Agent` (runtime), `Assistant` (chat panel), `Kanban` (board), `Definitions` (governed file loader), `Skills` (plugin registry + gallery), `Sow`/`SowSkill`, `Wireframe`/`WireframeSkill`, `Billing`, `StatusReport`/`StatusReportSkill` — all as plain JS objects in a single `<script>` block. (`Onboarding` is a *separate* existing module — product view-help tooltips — don't confuse it with `ProjectWizard`.)
- **Guided tour** — `Tour` is the product-level spotlight walkthrough of the main views (distinct from `Onboarding` per-view "?" help and from `Walkthrough`, the weekly sprint review). Step copy is static authored HTML only — never interpolate user data into it. Each step spotlights a `target` selector or renders centered (`center:true`), optionally navigating first via `view`; a missing/hidden target degrades to the centered layout so steps never dead-end. Offered once after **Load demo dataset** (`Tour.offer()` — non-blocking corner card); re-runnable any time from ⌘K ("Guided tour"). Both the offer and `Tour.start()` are blocked in customer (read-only) mode — the tour navigates to internal planning views that curtain hides. Finish/skip/decline all persist uiState `tour.done`.
- **Project detail panel tabs** (`DetailPanel.TABS`): `overview · delivery · value · sow · wireframe · billing · raid`. The old combined "Scope & Value" tab split into **Value** (outcomes only — Strategy linkage, Benefits, Success criteria) and **SoW** (scope info — Milestones & Dates, Stakeholders, Sponsor sign-off, Gate reviews — plus the linked Statement(s) of Work). **Wireframe** and **Billing** are their own tabs (`renderWireframes`, `renderBilling` from `Billing.quoteForProject`/`App.computeProjectCost`); `renderDocuments` was split into `renderSows`/`renderWireframes`. Legacy tab ids alias: `scope`→`value`, `setup`→`sow`. The tab strip scrolls horizontally.
- **New-project onboarding** is a conversational wizard: `DetailPanel.quickAdd()` (no template) → `ProjectWizard.open()`. Deterministic core (slots + parsers + prior-project prefill via `_suggestionsFor` + summary + `create()`), works with no AI; answer per-slot or paste `field: value` lines; only `name` is required; progress saves per customer in `uiState` (`onboarding.draft.<customer>`) so it resumes; "Use form" falls back to the classic `_openCreateWizard`. The classic 3-step form is unchanged and still reachable.
- **RAID-into-document** (SOW editor): "Pull from RAID" is a picker built from `Sow.raidCandidates()` — **only appropriate items** (open assumptions, or open high-severity risks score ≥ 12) are listed/selectable; `Sow.pullSelectedRaid()` brings in the chosen ones. `Sow.pullFromRaid()` (pull all fresh) is kept and delegates to the same candidate filter.
- **SOW accuracy/readiness helpers**: `Sow.figuresCheck(sow)` flags currency amounts in the document that don't trace to the generated quote (warnings, only when a quote grounds it); `Sow.quoteStaleReason(sow)` explains the drift behind a stale quote; `Sow.regressionWarnings(sectionId, newContent, def)` re-validates an AI redraft before accept (min-words regressions); `Sow.resolveAllFlags/resolveAllComments` bulk-resolve (one undo); `validate()` adds a phase-alignment warning (Deliverables phases vs the linked project's `delivery_config.phase_order`). The editor side panel leads with "N issues before Approve"; per-section "Suggest edit" is always available in Review (disabled with a hint when no feedback), and empty sections get `SowSkill.uiDraftSection` (AI-draft grounded in source + project facts, followed by a best-effort `SowSkill._selfCritique` review pass that tightens the draft to the style rules + grounding before it is shown).
- **SOW playbook (governed review)**: each `definitions/sow*` set ships a `playbook.json` (manifest key `playbook`) — preferred commercial positions, tiered fallback wording, hard never-accept rules; tiers `preferred|fallback|never_accept`. Machine-checkable shapes (`must_contain` string-or-alternatives, `must_not_contain`, `numeric {pattern,min,max,label}`) run deterministically in `Sow.validate` via `Sow._playbook(customer)`/`playbookCheck` (non-empty sections only, no model). Never-accept deviations become errors when `approval_requires` includes **`playbook_clean`** (both shipped sets do); other tiers are warnings. `Sow.insertPlaybookFallback` inserts the governed fallback deterministically (once per rule, `section.sources` kind `'playbook'`). The editor's side panel gains a Playbook group (index-based handlers over `SowSkill._playbookDevs`): per-deviation "Insert fallback wording" + AI "Apply on-playbook wording" (`uiPlaybookRedraft` — lands in the existing `_redraft` Accept/Reject redline; the redline card also re-checks pending content via `Sow.playbookProblemsForContent`), and "Run playbook review" (`uiPlaybookReview`) judges `ai_check` rules per section — **advisory only**, findings transient (`_playbookAi`, never in `App.data`), unknown rule ids dropped, never feeds validate/risk.
- **SOW risk score (tiered approval gates)**: `Sow.riskScore(sow, def)` is a deterministic rubric over named checks only — playbook deviations by tier (10/2/1), flags (3), open comments (2 each), untraced figures (2), empty/thin required (3/2), stale quote (4), non-build-ready attached wireframe (4) — every point traceable in `items[]`. Tier: Green < `RISK_AMBER` (8) ≤ Amber < `RISK_RED` (16) ≤ Red. **Red hard-blocks Approve** (a `Sow.validate` error, token-independent); **Amber** approves only via `Sow.setStatus(id,'Approved',def,{overrideRationale})` — the editor prompts with a breakdown modal (`_openRiskOverride`), and the typed rationale is recorded in `history[]` (`risk_override`) and the audit log (`sow_risk_override`). Calibration note: the shipped playbook's preferred/fallback noise on a plain filled doc stays Green — keep it that way when adding rules. AI narration (`uiExplainRisk`) is optional, grounded only in the rubric fact pack, rendered escaped, hidden with no AI.
- **SOW whole-document review (sow-doc-review)**: `Sow.docReviewLints(sow, def)` = deterministic, model-free cross-section lints folded into `Sow.validate` **warnings** (never errors, never risk points — keeps plain docs Green): `consistencyLints` (Scope↔Out-of-scope shared bigrams; Timeline dates outside the linked project's sprint calendar; named people absent from Roles & Responsibilities) + `styleLints` (word budget vs the ~1,800-word sow-style rule, bullet-verb rule via `_NON_VERB_BULLET_START`, British-English spellcheck via `_AMERICANISMS`) + reverse deliverables/`phase_order` alignment. All pure/testable. The optional AI full-pass `SowSkill.uiDocReview()` reads every section together (only way to catch cross-section contradictions), grounded in the full stack (`groundingFor`/`wireframeGroundingBlock`/quote totals + the deterministic lints), and returns per-section edits that land as ONE batch of redline cards (`_docReview`); **Accept-all = one `App.runBatch`** (single undo). Unknown section ids are dropped by a post-filter (no schema enum, so a stray id never fails the whole response); no-op edits dropped.
- **SOW precedent-grounded drafting (sow-precedent)**: `Sow.precedentVersions(sow, sectionId)` is a pure local query — the customer's last `PRECEDENT_N` (3) **Approved** SoWs of the SAME `template_id`, that section's text, newest first (excludes the current SoW + empty sections). `Sow.precedentBlock(sow, sectionId)` mirrors `wireframeGroundingBlock` (returns '' when none) and is folded into the four prompt builders (`uiDraftSection`/`uiRedraftRun`/`uiSuggestEdit` + `_selfCritique` via its grounding arg). Model-free path: a per-section "Precedent (N)" toggle lists prior Approved versions read-only with one-click "Copy from precedent" → `Sow.copyFromPrecedent` records provenance (`section.sources` kind `'precedent'`, ref = source SoW id, once per source; undoable). Precedent source chips deep-link to the source SoW (index-based handler — no untrusted id in onclick).
- **SOW risk-adjusted commercials (sow-risk-quote)**: `Forecast.effortPointBands(customer, plannedPoints, opts)` is a pure Monte-Carlo — samples the customer's completed-sprint completion **reliability** (velocity `ratio` history) so effort = planned / ratio, reading P50<P80<P95 off the distribution (`RATIO_FLOOR` clamps catastrophic sprints; `opts.rng` injectable for deterministic tests). `Billing.quoteWithBands(project, opts)` returns the POINT quote (totals unchanged so **`Sow.quoteIsStale` keeps working**) plus a `bands` block pricing P50/P80/P95 at `hours_per_point × hourly_rate`; the named **contingency reserve** = chosen-confidence (default P80) − P50. `Sow.setQuote` always stores bands (re-quote preserves the author's `applied`/`confidence`); `Sow.setQuoteMode(id, applied, confidence)` toggles risk pricing + re-renders Commercials via `Billing.quoteAsText`/`quoteBandsText` (figures Billing/Forecast only). `figuresCheck` allows the band amounts; the sow-quoted set gates approval on the **`contingency_priced`** token (blocks when bands are sufficient-but-unapplied; honest pass-through when `bands.insufficient` — < `Forecast.MIN_HISTORY`). AI writes ONLY the client-facing contingency-justification prose (`uiContingencyNote`, no figures), landing via the existing `_redraft` accept card.
- **No emojis** — all icons are inline SVGs throughout.
- **Schema-driven Projects table** — `Dashboard.COLUMNS` is the single source of truth for header (`renderHeader`), row body (`buildRowHtml`), the column picker (`ColumnPicker`), and the inline editor (`openQuickEdit`). Add a column = one entry. Inline edits dispatch on `col.edit.type` (text/number/date/select/textarea/sprint/rag/derived) and write through `App.updateProject`. Visibility/order/width persist globally via `App.uiStateSet('dashboard.columns', …)`. Single-click row opens the detail panel (deferred ~280 ms so a double-click on a `data-quick-edit` cell can take over and open the inline editor instead). `.project-table` uses `table-layout: fixed` so column widths are authoritative.
- **Customer-scoped & the All filter** — `App.activeCustomer` is always a real working customer (defaults to the first; every authoring/creation flow reads it, so it is never null). The header selector adds an **"All customers"** option that sets `App.allCustomers` (persisted in `pcc...-allCustomers`, never enabled in `customerMode`). `allCustomers` only takes effect on aggregate-capable views — `App.ALL_CAPABLE_VIEWS` (Projects/Board/RAID/Roadmap/Backlog/Capacity/Documents/Activity/Portfolio). Drive a view's scope through the view-aware helpers: `App.scopeCustomer()` (returns `null` = aggregate, else `activeCustomer`) and `App.matchesCustomer(c)` (predicate). A view aggregates only when `App.isAllScope()` (= `allCustomers && !customerMode && current view ∈ ALL_CAPABLE_VIEWS`); on every other view "All" silently falls back to the working customer (titlebar shows "· this page shows one customer"). When adding a customer-scoped read view, route it through `scopeCustomer()`/`matchesCustomer()` and add it to `ALL_CAPABLE_VIEWS` if aggregation is meaningful; leave authoring/per-customer-allocation views (Sprint, Strategy library, Settings) on `activeCustomer`.
- **Skill colors** — defined in `Sprint.SKILL_COLORS`. Avoid green/amber/red (RAG confusion). Current: Indigo (Req), Cyan (Tab), Blue (DE), Violet (DS), Pink (UAT).
- **Schema-driven Kanban cards** — `Kanban.CARD_FIELDS` mirrors the `Dashboard.COLUMNS` pattern: adding a card field = one entry. Transitions go through `Kanban.moveCard` → `App.updateProject(id, 'status', value, 'board-drag')`. The board carries the developer dimension: cards show assignee avatars and there is a **"By assignee" swimlane**, both derived from `Kanban._assignees(p)` (distinct `skill_splits[].assigned_to[].member`) — so they populate once allocations are applied (Auto-Allocate/solver persist `assigned_to`); fresh/unallocated data shows "Unassigned". **Board enhancements (K1–K10)**: cards surface dependency state (`_blockCounts` → "Blocked by N"/"Blocks N" chip + red left border), aging (`_isStale` via `App.getStaleThreshold` → dimmed + "Nd idle") and **time in status** (`_statusDays` from `project.status_changed_at`, stamped centrally in `App.updateProject` when `field==='status'`, backfilled in migration). The toolbar adds manager/category dropdowns, quick-filter chips (Blocked/At-risk/Stale), and a sort selector (priority/WSJF/deadline/age/points via `Kanban.sortCards`/`sortMode`); columns show a **Σ SP subtotal** (`_sumPts`) and are **collapsible** (per-customer `uiState` `board.collapsed`), as are swimlanes (`board.lanes`). WIP limits gain **soft/hard enforcement** on the drag path only (`_wouldExceedWip` + `wipHard()` toggle — `moveCard` stays unguarded so programmatic/test moves are deterministic). A per-card **⋯ actions menu** (`openCardMenu`/`menuMove`) moves cards without dragging (touch-friendly), and cards support **keyboard move** (←/→ across visible columns) + ARIA roles (`onCardKey`). All board prefs key through `Kanban._uiKey(name)` (per customer).

## AI Layer (WS1–WS6)
- **Provider profiles live ONLY in localStorage** (`pcc_ai_settings`), never in `App.data` — keys can never reach exports or the repo. Configure in Settings → AI & Assistant: multiple profiles, per-task defaults (chat / drafting / design).
- **Adapters** in `AI.ADAPTERS`: `openai` (any OpenAI-compatible endpoint incl. Groq, Ollama/LM Studio/vLLM/llama.cpp — Groq ships as a one-click preset in `AI.PRESETS.groq`, base URL `https://api.groq.com/openai/v1`), `anthropic`, `gemini`, `mock` (tests only — `AI.ADAPTERS.mock.program([...])`; program `{chunks:[...]}` to exercise streaming). Each has pure `buildRequest`/`parseResponse` so tests never network. All transport goes through `AI._request` (timeout, retry/backoff, Retry-After, CORS guidance, cancellation). **Streaming**: `AI.stream` dispatches to `streamChat` (SSE via `AI._streamRequest`/`_sseSplit`; pure `_applyStreamEvent` per adapter) and falls back to buffered chat delivering one delta — callers never branch. The Assistant renders live tokens; tool-call rounds reset the partial.
- **Capability negotiation**: `AI.capabilities(profile)` → `{tools, streaming, json, vision}`; models without native tool-calling run the same `AgentTools` registry through a constrained-JSON fallback (`Agent._runJsonFallback`) with strict parse + repair loop. Never let a feature exist only on the native path. **Vision (W1a)**: messages may carry `images:[{mime,data}]` (bare base64); every adapter's `buildRequest` translates them (openai `image_url`, anthropic base64 `source`, gemini `inline_data`; mock records them). `vision` is a model-name heuristic (`_visionForProfile`, recognises cloud + local families incl. llava/llama3.2-vision/qwen-vl/gemma3) with an explicit `profile.vision` override. Images travel only in the request — never persisted into `App.data` (exports stay lean). The wireframe skill grounds drafts/refines in a pasted/uploaded screenshot + referenced Tableau thumbnails when `capabilities(profile).vision`, else falls back to text-only grounding.
- **AgentTools registry**: declarative descriptors; read tools filter by `ctx.customer` (and aggregate across every customer when `ctx.allScope` — set from the "All customers" filter so the Assistant can answer portfolio-wide); **write tools return proposals** (`{summary, changes, apply()}`) — they never mutate. `apply()` routes through `App.addProject`/`App.updateProject` with source `'ai'`, so AI writes are confirmed, audited and undoable. Tool args are validated (`validateArgs`) before any handler runs. **Skills-as-tools** (`draft_sow`, `draft_wireframe`, `generate_report`) are write tools whose `apply()` launches the governed skill/Reports engine, so the Assistant can *produce* governed documents on confirm, not just read/edit fields. **NL-to-action coverage (Phase 1.1)** extends the write surface beyond project fields/RAID to dependencies (`manage_dependency`), customer milestones (`set_milestone`), team capacity (`update_capacity`, incl. per-sprint overrides), strategy (`update_strategy` — objectives + metrics via `Objectives`/`Metrics`), prepaid billing blocks (`update_billing_arrangement` via `Billing.addArrangement`/`removeArrangement`, which take an optional `source`), and governance (`update_governance` — add forum / log project decision); paired reads `list_dependencies`/`list_milestones`/`list_objectives` ground them. Each `apply()` routes through the canonical mutator (or replicates its pushUndo+logChange+markDirty+save+notify when the entity has only UI-bound handlers — e.g. dependencies/milestones/governance), audits `'ai'`, and is undoable. Note `App._save` is a guarded no-op (never defined): `Objectives`/`Metrics` mutators only touch memory, so their callers must persist explicitly. **Triage/hygiene (Phase 1.2)**: `tidy_portfolio` is a read-only deterministic scan that emits one confirmable proposal per fix (duplicate-RAID closes; a single atomic priority-normalisation to a clean 1…N) — the proposals ride the batch card. **⌘K→agent bridge (Phase 1.3)**: `CommandPalette._build()` adds an "Ask AI" group whose entries call `Assistant.ask(intent)` (scope = current customer/all-filter; one `VIEW_PROMPTS`-driven view entry + a context entry when a project is open).
- **Assistant**: per-customer in-memory threads (chat history never enters `App.data`; opt-in localStorage persistence via the Remember toggle — message text only, proposals never persisted); under the "All customers" filter it runs in a separate `__all__` thread and reads portfolio-wide. Citations deep-link entities; proposals render diff cards with Confirm/Discard. A proactive "since last week" briefing (`_computeBriefing`, from the `recent_changes` tool — no model call) shows on open until dismissed; answers show the chained tool steps (`_traceHtml`); quick-prompt chips are scope- and view-aware (`_suggestions`).
- **Skills**: one descriptor in `Skills.REGISTRY` per skill (see `SKILLS.md`). Output must land as a real entity (`data.sows`, `data.wireframes`, projects) and conform to its definition file before leaving Draft. `Sow.validate` / `Wireframe.checkConformance` enforce structure; content nuance is never flagged.
- **Untrusted content rules**: uploaded documents are wrapped in `<untrusted_document>` tags with a never-follow-instructions system rule; every model/document string rendered goes through `Dashboard.esc()`; `Dashboard.esc()` does NOT escape double quotes — never interpolate untrusted values into double-quoted onclick attributes (use index-based handlers).
- **Entity mutators contract**: `App.pushUndo(label)` BEFORE mutating (see `Sow`/`Wireframe` `_persist` note) — snapshots must capture pre-change state.
- **Agent memory (Phase 0.1)**: `data.agent_memory = {goals, facts, worklog}` — durable, **customer-scoped** (each entry carries `customer`), export-safe (provider keys never reach `App.data`). `AgentMemory` is the API (`goals/facts/worklog/addGoal/addFact/remove/logRun/contextBlock`). `Agent._systemPrompt` folds the active customer's pinned goals/facts into context every run via `AgentMemory.contextBlock(ctx.customer)`. Tools: `list_memory` (read), `set_goal`/`remember_fact` (proposal-gated writes, audited `'ai'`). Memory edits are undoable; the worklog records each batch/auto run.
- **Batch runner & autonomy (Phase 0.2/0.3, user-initiated only — NO scheduler/triggers)**: `App.runBatch(label, applyFns)` applies many proposal `apply()`s as ONE undoable, audit-grouped batch — it `pushUndo`s once and sets `App._batching` so the per-`apply()` `pushUndo` calls are suppressed (one Ctrl+Z reverts the whole batch; entries share a `run_id` via `beginAuditRun`). The Assistant groups a run's proposals: 1 → existing single card; ≥2 → one **batch card** (`kind:'batch'`) with per-change toggles + Confirm-all/Discard-all (`confirmBatch`/`discardBatch`/`toggleBatchItem`). **Per-run policy** lives in UI state (`agent.policy = {mode:'propose'|'auto_apply', maxChanges}`, never `App.data`): `propose` (default) is the dry-run — shows every change, mutates nothing until confirmed; `auto_apply` applies up to `maxChanges` in one `runBatch`, the overflow downgrades to a pending card. Set via the Assistant footer strip (`Assistant.policy()/setPolicy()`). Every applied batch logs an `AgentMemory.logRun` worklog entry.

## Data Model Key Facts
- **Customer** is always single-select and mandatory; configured in Settings → Customers.
- **Delivery Config** per project: `delivery_config` with toggles (include_req, include_de, include_ds, include_tableau, include_uat, include_hypercare) and `phase_order` array
- **Delivery Phases** (6 possible): Requirements, Data Sourcing, Data Engineering, Data Science, Tableau, UAT. Each has status + optional story points.
- **Skills** (5 with points): Requirements (size_requirements), Tableau (size_tableau), Data Engineering (size_engineering), Data Science (size_data_science), UAT (size_uat_adoption)
- **Delivery Pipeline**: Driven by each project's `delivery_config.phase_order`. The Solver reads this per-project.
- **skill_splits**: Allocation across sprints with status (pending/in_progress/complete) and completed points. Optional `work_start_date` / `work_end_date` per split narrow the Gantt bar to the actual work window (Issue 4).
- **Sprints**: 4-week dev + 1-week hardening = 5-week cycle. End date auto-computed from start_date.
- **Team Members**: `available_points_per_sprint` is available for ANY skill (primary + secondary). Per-sprint overrides via `sprint_overrides`.
- **FY boundary**: 1 June each year
- **Status options**: Not Started, In Progress, On Hold, At Risk, Blocked, Complete, Closed (also the Kanban board's columns)
- **RAG**: rag_schedule, rag_resourcing, rag_scope — labelled Schedule Health, Resource Health, Scope Health
- **WSJF prioritisation**: Projects may set `business_value`, `time_criticality`, `risk_reduction_opportunity` (each 1–10) and `moscow` ("Must"/"Should"/"Could"/"Won't"). When any WSJF input is populated, `App.calculateWsjf(project)` drives scoring; otherwise the legacy hybrid (status × RAG × risk × size × deadline) is used. Solver sort: hard_deadline → MoSCoW band → WSJF → priority.
- **Story points are integers** everywhere except statistics (velocity avg, days-per-SP). Use `App.toInteger(v)` to parse, `App.fmtPoints(n)` to render. `App.fmtAverage(n, decimals)` for sanctioned decimal statistics.
- **R12 concurrent guard**: a member is never assigned to two overlapping deliveries unless both are in `concurrentOverlapAllowedSkills` (default: Req + UAT). Toggle via `enforceConcurrentSinglePerson`.
- **Wireframe sign-off (follow-on)**: wireframes carry a lifecycle `status` **Concept → Approved → Superseded** (`Wireframe.STATUSES`/`setStatus` — Approved gated on `buildReady`; Superseded retires a concept with no gate; audited + undoable; status chip in the list + editor). SOWs carry `wireframe_ids[]`; `Sow.toggleWireframe` attaches same-customer wireframes for sign-off. `Sow.validate` blocks approval while any attached (non-Superseded) wireframe isn't build-ready; `Sow.setStatus('Approved')` **co-signs** every attached wireframe inside the SoW's single undo (`App._batching` guard suppresses their nested `pushUndo`). The SoW print/PDF appends each attached wireframe as a signed-off appendix (status + `fieldMap` + `acceptanceChecklist`). `Sow._wireframeDef(customer)` resolves the tableau definition for the readiness check. **Wireframe-grounded drafting**: `Sow.wireframeGrounding(sow)`/`wireframeGroundingBlock(sow)` summarise the attached (non-Superseded) wireframes (name + status + answered metrics + `fieldMap`) as a `<wireframe_facts>` block folded into every SoW draft/redraft/suggest-edit prompt, so the Scope/Deliverables describe the dashboards actually being built (never inventing components/metrics beyond them).
- **SOWs** (`data.sows`): customer-scoped, optional `project_id`, `status` Draft/Review/Approved, `wireframe_ids[]` (attached for sign-off), `sections[]` in definition order with `flagged`/`flag_reason`/`comments` (each comment `{at,text,resolved}`), `history[]`. Approval gated by `Sow.validate` against the selected `definitions/sow/` set — `approval_requires` may include `comments_resolved` (open comments block Approve) and `no_unresolved_flags`. **Review redline (S4)**: `Sow.setStatus` snapshots each section's content into `section.baseline`/`baseline_status`/`baseline_at` on Review/Approved transitions; the editor's per-section "Compare" diffs current vs that baseline (struck-old/new). `Sow.resolveComment` flips a comment's `resolved` (audited/undoable); legacy comments migrate to `resolved:true` so they never retroactively block. **AI review edits (follow-on)**: `SowSkill.uiSuggestEdit(sectionId)` (the per-section "Suggest edit" button, shown when not Approved and the section has a flag or open comment) builds the instruction from the section's `flag_reason` + open `comments[]` (no typed input), grounds like `uiRedraftRun`, and reuses the redraft redline/Accept UI (`_redraft.fromReview`); on accept `uiRedraftAccept` applies `redraftSection` + `resolveComment`(each addressed) + `resolveFlag` as ONE `App.runBatch` (single undo, audited `'ai'`).

## Strategy Entities — Persona vs Person

The strategy model splits the role from the human that fills it. Get this split right or the cascade lies.

- **Persona** owns the *role archetype*: `name` (archetype label like "CFO" — there is no separate `role_title`, the name IS the label), `parent_persona_id` (org hierarchy), `definition`, `key_responsibilities`, `stakeholders`, `goals`, `pain_points`, `information_needs`, `business_questions`, `metric_holdings` (role-owned targets), `notes` (role-level commentary — "vacant", "pending hire").
- **Person** owns the *individual filling a seat*: `name` (real human name), `role_title` (their actual job title, may differ from the persona archetype), `email`, `department`, `region`, `persona_id` (which seat), `manager_id`, `active`, `target_overrides` (per-metric customisation against the persona's holdings), `communication_prefs` (per-individual), `notes` (individual history — "started Mar 2025", "on parental leave").
- **RACI keying**:
  - `metric.raci_defaults[role]` → array of persona IDs (the role template).
  - `metric.raci[role]` → array of person IDs (the live assignments).
  - `_seedRaciFromDefaults` populates `raci` from `raci_defaults` whenever a Person's persona changes; manual edits to `raci` diverge the individual from the template — divergences surface in the Metrics cascade.
- **Held metrics resolution**: Persona's `metric_holdings` are the canonical role-level targets. `Person.effectiveHoldings()` overlays any matching `target_overrides` so per-person variation shows up without duplicating the holding.
